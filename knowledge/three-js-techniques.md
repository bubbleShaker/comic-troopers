# このプロジェクトで使った three.js の技法

実装中に出てきた「なぜこう書いたか」の記録。コードのコメントより長く説明したいものを置く。

## 背面法の輪郭線（アウトライン）

コミック調の黒い縁は、**同じ形をひとまわり膨らませて裏面だけ描く**ことで作っている。

```
本体を普通に描く（表面）
   ↓
法線方向に少し膨らませたコピーを、裏面だけ描く
   ↓
本体からはみ出した部分＝縁 だけが見える
```

`src/render/toon.ts` の `createOutline` がこれで、頂点シェーダで `position + normal * thickness` している。

なぜポストプロセス（画面全体のエッジ検出）にしなかったか: 追加のレンダーパスが要らず、モバイルで軽いから。
欠点は、形状ごとにメッシュが1つ増えること（描画呼び出しが倍になる）。今の規模では問題にならない。

### 頂点の「溶接」が要る理由

`flatShading` 用のジオメトリ（`OctahedronGeometry` など）は、面ごとに頂点が分かれている。
同じ位置に複数の頂点があり、それぞれ別方向の法線を持つ。

そのまま法線方向へ膨らませると、**同じ位置にあった頂点がバラバラの方向へ飛んでいき、縁が裂ける**。

`mergeVertices()` で同一位置の頂点をまとめ、`computeVertexNormals()` で平均した法線を計算し直したものを
輪郭専用のジオメトリとして使っている。

## トゥーンシェーディングのグラデーションマップ

`MeshToonMaterial` は、明るさをそのまま使わず「グラデーションマップ」というテクスチャで**量子化**する。

```
通常のライティング:  0.0 ────────────────► 1.0  （なめらか）
3階調のトゥーン:     0.33 │ 0.66 │ 1.0        （段になる）
```

`createToonGradient(3)` は幅 3px・高さ 1px の `DataTexture` を作り、`NearestFilter` で補間を切っている。
補間を許すと段の境目が滑らかに繋がってしまい、セルシェードにならない。

## 弾のすり抜け（トンネリング）と線分判定

弾は毎秒 46m 進む。20fps だと 1 フレームで **2.3m** 動く。一方、敵の当たり半径は 1.15m。

```
フレーム N:    ●弾              ◆敵
フレーム N+1:                        ●弾   ← 敵を飛び越えている
```

移動後の1点だけで距離を測ると、この間に敵がいても当たらない。
そこで「移動の軌跡（線分）と敵の中心との最短距離」で判定している（`distanceToSegment`）。

高速な弾を扱うゲームでは定番の対処。逆に、遅い敵の接触判定は点で十分なのでそのままにしてある。

## 縦持ちの視界とカメラの引き

透視投影の `fov` は**垂直方向**の視野角。横に見える範囲は `fov × アスペクト比` で決まる。

スマホ縦持ちのアスペクト比は約 0.46 なので、垂直 55° に対して水平は極端に狭くなる。
そのままだと「射程内なのに画面に映っていない敵」が生まれる。

対策として、カメラの距離を `1 / アスペクト比` 倍している。

```ts
const zoom = clamp(1 / min(aspect, 1), 1, 2.6)
```

こうすると、画面比が変わっても**横に見える実距離がほぼ一定（約 22m）**になる。
射程やフィールドの広さは、この 22m を基準に決めている。

## メッシュのプール

敵や弾は毎フレーム増減する。その都度 `new THREE.Mesh()` と `dispose()` を繰り返すと、
ゴミ集め（GC）が走ったタイミングでフレームが飛ぶ。

`src/render/pool.ts` は、必要な数まで作ったら以降は `visible` の on/off だけで使い回す。

```
begin()  → 今フレームの割り当てをリセット
take()   → 1つ借りる（足りなければその時だけ作る）
end()    → 使わなかったぶんを隠す
```

### プールで踏んだ罠

枠は配列の先頭から順に割り当てられる。**敵が1体死ぬと、それ以降の敵は1つ前の枠へずれる**。
このとき `mesh.rotation.y += dt` のような**加算**で回転させていると、ずれた敵が前の住人の角度へ飛ぶ。

そこで回転は加算ではなく `world.time` と `enemy.id` から毎フレーム計算している。
プールを使うときは「枠に状態を残さない」のが原則。

## dt のクランプ

タブを離れて戻ると、`requestAnimationFrame` の間隔が数秒空くことがある。
その `dt` をそのまま使うと、敵が一瞬でワープしたり当たり判定が飛んだりする。

```ts
const dt = Math.min((now - prev) / 1000, 1 / 20)
```

上限を 1/20 秒に切ることで、どんなに間が空いても「20fps 相当の1フレーム」として扱う。

副作用として、**フレームレートが 20 を下回るとゲーム内時間が実時間より遅く進む**。
60 秒のランが実時間では長くかかる。実機で 60fps 出ていれば起きないが、
ヘッドレスのソフトウェア描画では実際に 75 秒ほどかかった。

## WebGL コンテキストの消失

モバイルではタブのバックグラウンド化やメモリ逼迫で WebGL コンテキストが失われる。
何もしないと以後ずっと黒画面になる。

- `webglcontextlost` を捕まえて `preventDefault()` する（しないと復帰イベントが来ない）
- 失っている間は `render()` を呼ばない
- 復帰したら再びサイズを測り直す

`src/render/scene.ts` でこれらを面倒見ている。
